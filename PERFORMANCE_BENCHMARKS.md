# ViewAlign Performance Benchmarks

Generated by `tests/benchmark/run-all.js` (`node tests/benchmark/run-all.js`),
run 2026-08-20. Reproducible - rerun the script to regenerate these numbers
on any machine; methodology is documented below for the manuscript's
Methods section.

## Methodology

- **Scroll latency**: for each alignment size, load a synthetic FASTA
  (deterministic, seeded, `ACGT` repeating pattern) via the real UI load
  path, then measure wall-clock cost of 6 consecutive scroll-refresh cycles
  in both Full/DOM mode (`_refreshUnifiedWindowOnScroll`, windowed DOM
  rendering) and Canvas mode (real `WheelEvent` dispatch, timed via a
  double-`requestAnimationFrame` callback so the measurement covers the
  actual `draw()` execution, not just `requestAnimationFrame` scheduling
  overhead).
- **Typing latency**: load a 4M-residue alignment (200 seq × 20,000 col,
  a realistic editing target size, not an extreme case), enable GeneDoc
  residue-edit mode, dispatch 10 real `KeyboardEvent`s, measure per-keystroke
  wall-clock cost.
- All measurements via headless Chrome (playwright-core driving the
  system-installed Chrome directly) - no synthetic/mocked timing.
- Only sizes at or above `ALIGN_CRAZY_VOLUME` (5,000,000 residues) are
  tested for scroll latency, since that's the threshold at which the
  windowed-DOM rendering path actually activates; testing below it would
  measure the unwindowed path instead, which is a different code path with
  different (also good, but not what this benchmark is about) performance
  characteristics for typical-sized alignments.

## Results (2026-08-20)

| Alignment size | Load time | DOM scroll (avg/max) | Canvas scroll (avg/max) |
|---|---|---|---|
| 6M residues (500 seq × 12,000 col) | 777 ms | 49.7 / 54.5 ms | 49.0 / 67.7 ms |
| 15M residues (1,000 seq × 15,000 col) | 1.6 s | 52.2 / 61.1 ms | 53.5 / 71.1 ms |
| 40M residues (2,000 seq × 20,000 col) | 3.9 s | 49.0 / 60.7 ms | 44.3 / 49.4 ms |
| 100M residues (2,000 seq × 50,000 col) | 9.5 s | 53.8 / 60.0 ms | 64.1 / 75.5 ms |

**Typing latency** (4M-residue alignment, GeneDoc residue edit mode):
1.0 ms average, 1.9 ms max per keystroke.

## Key finding

**Scroll-refresh cost is flat (~50-65ms) across a >16x range of alignment
size** (6M to 100M residues), for both the windowed-DOM renderer and the
Canvas renderer. This is the direct, measured result of the windowing work
done this session (see `todo.md`'s performance section and the git history
around the v177-v179 tags / `fix-large-alignment-load-hang` branch) -
scroll cost scales with the *visible viewport*, not the *total alignment
size*, by design. Load time does scale with total size (expected - the full
alignment must be parsed and an initial render performed), but even the
100M-residue case loads in under 10 seconds.

## Known limitation of this benchmark

This is a synthetic, repeating-pattern alignment (`ACGT` repeated), not
biological sequence diversity - chosen for reproducibility (deterministic,
no external data dependency) but it does not exercise conservation/
consensus computation cost the way a real diverse alignment would. The
consensus/conservation pre-computation (`preCalculateConservation`,
`_computeVarSites`) happens once at load time regardless of scroll
behavior, so this shouldn't affect the scroll-latency numbers above, but a
real biological dataset's *load* time could differ from what's shown here.

## Not yet done: comparison against Jalview/UGENE

These numbers characterize ViewAlign in isolation. A head-to-head
comparison against Jalview or UGENE at equivalent alignment sizes has not
been run - those are desktop Java applications not present in this
environment, and would need to be benchmarked separately (ideally on the
same machine, same alignment files, for a fair comparison) before any
comparative claim goes in the manuscript.
